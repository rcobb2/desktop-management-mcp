# Troubleshooting Intune deployment issues

Route the question to the right tool first — several plausible-looking Graph resources for this are either dead, permission-gated, or empty in practice, and re-discovering that live wastes a turn. Everything below is confirmed against this tenant unless marked otherwise.

## Which tool for which question

- **"Which devices have an issue with policy X?"** → `intune_get_configuration_conflicts` (classic device configuration profiles only). It calls `deviceConfigurations/{id}/deviceStatuses` directly off the policy — this names real devices with no group-membership resolution needed, so it works even without the `Device.Read.All` Graph permission gap below. Confirmed live: named all 7 real devices in error on a real profile, plus surfaced one stale row with an empty device name (fell back to the assigned user's UPN).
- **"Why does *this specific* device have an issue?"** → `intune_troubleshoot_device_policies` (deviceName/serial in, full config+compliance state dump + heuristic issues out) or `intune_troubleshoot_policy` (one device × one policy, correlates assignment scope with deployment state — catches "device isn't actually in scope" cases the state dump alone won't).
- **"Why did app X fail to install?"** → `intune_get_app_install_status`, backed by the Reports API (see dead-end below — do not reach for the obvious-looking `mobileApps/{id}/deviceStatuses`). Gives real per-device `installStateDetail` failure reasons (`autoInstallDisabled`, `dependencyFailedToInstall`, etc.) plus raw `errorCode`, not just a pass/fail count.
- **"What's this profile actually configured to do, and what's it scoped to?"** → `intune_get_configuration_profile` for the payload, `intune_get_policy_assignments` for scope (reads `resolvedTargets`, not `assignments[].target` — see bug note below if extending this).
- **Settings Catalog policies** have none of the above navigation properties — no `deviceStatuses`, no `deviceStatusOverview`, no conflict summary. The only lever is the Reports API's `getConfigurationPolicyNonComplianceReport` action, not yet wrapped as a tool here. `intune_get_configuration_conflicts` correctly returns `supported: false` for these rather than a silently-empty result — don't interpret that as "no conflicts."

## Dead ends — don't spend time here

- **`mobileApps/{id}/deviceStatuses` and `.../installSummary` are dead**, not just "deprecated since May 2023" as their own docs still claim — confirmed live, both 400 ("Resource not found for the segment") at **both** v1.0 and beta. `intune_troubleshoot_app`'s heuristic report still calls this internally and silently degrades to "no device app state" for every app as a result — a known, currently-undocumented-elsewhere gap in that tool. The real replacement is `POST /deviceManagement/reports/retrieveDeviceAppInstallationStatusReport` (v1.0, confirmed live) — but call it with native `fetch`, not the Graph SDK client's `.post()`. Confirmed live: the SDK returns a bare `{}` for this exact endpoint/body with no thrown error (the response is a `{SessionId, TotalRowCount, Schema, Values}` tabular shape, `Schema` a column list and `Values` an array of row-arrays in that order — not the SDK's expected shape), while an identical raw `fetch` with the same token/body returns real rows. `InstallState`/`InstallStateDetail` come back as enum integers, not strings — see `IntuneClient.INSTALL_STATE_MAP`/`INSTALL_STATE_DETAIL_MAP` in `src/intune/graph-api.ts` for the confirmed int→string mapping; unmapped detail codes render as `unknown (code N)` rather than a guess.
- **`deviceConfigurationConflictSummary` (beta) 500s tenant-wide, persistently** — confirmed with and without `$top`, same generic "An internal server error has occurred" both times. This is a genuine Microsoft-side issue in this tenant, not a request-shape problem to keep iterating on. `intune_get_configuration_conflicts` already catches this and reports it via `conflictSummaryError` rather than failing the whole call — if it starts working again, that's the signal, not a code change here.
- **`deviceConfigurationStates[].settingStates` comes back as an empty array** even for a policy whose whole-policy `state` is `"conflict"` — checked live at both v1.0 and beta. There is currently no way to learn *which setting* is conflicting or *which other policy* is fighting it for a given device short of the (broken) conflict-summary endpoint above. Don't assume `settingIssues` in `getDevicePolicyDeploymentTroubleshooting`'s output will be populated — today it's reliably empty.
- **`deviceConfigurationStates`/`deviceCompliancePolicyStates` sometimes return literal duplicate rows** for the same policy on the same device (identical id/state/version) — confirmed live, 3 of 6 assigned policies duplicated on a real device, 3 not, no visible pattern. Raw Graph behavior, not a client bug. `IntuneClient.dedupeById()` handles this centrally in `getDevicePolicyDeploymentTroubleshooting` — if you add a new method reading either of these two collections, dedupe by `id` there too rather than assuming the API already did.

## Permission gap affecting device-name resolution

`intune_get_group_members` correctly requests `microsoft.graph.device/deviceId` and `.../operatingSystem` with the OData type-cast `$select` syntax (necessary on this polymorphic `/groups/{id}/members` collection), but device rows still come back with `displayName: null` for this tenant's app registration. Confirmed root cause: it's a missing Graph **Application** permission (`Device.Read.All`), not a query bug — a direct `GET /devices/{id}` with this app's own token 403s cleanly, while the group-members endpoint just silently nulls the fields it can't authorize instead of erroring. Granting it requires Global Administrator or Privileged Role Administrator (Cloud Application Administrator, the role available when this was last investigated, is deliberately blocked by Microsoft from self-granting Graph API permissions — don't retry that grant as the same role, it will fail the same way). Until granted, prefer the policy-scoped `deviceStatuses` endpoints (see above) over resolving a device by walking group membership — they don't need this permission at all.

## Bug pattern worth checking for elsewhere

Two markdown-rendering bugs were found this way and are now fixed — both were cases of the renderer reading a field shape the client method doesn't actually return: `intune_get_policy_assignments` read `a.target?.groupDisplayName` when the real shape is a flat `resolvedTargets[]` array with `.displayName`; `intune_troubleshoot_device_policies` treated `issues` (an object `{configurationPolicies, compliancePolicies}`) as an array. If a markdown tool's output looks suspiciously empty or generic ("Unknown", "No issues detected") for data you can independently confirm is non-empty via `response_format: "json"`, suspect this pattern before suspecting the underlying Graph call.
