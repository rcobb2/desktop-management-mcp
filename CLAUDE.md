# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run build          # compile TypeScript to dist/
npm run clean          # remove dist/
npm run start:jamf     # run standalone JAMF MCP HTTP server (port 3001)
npm run start:intune   # run standalone Intune MCP HTTP server (port 3002)
npm test               # compile (tsconfig.test.json) + run integration tests against live JAMF and Intune, plus the auth unit tests
npm run test:write     # same, but enables destructive write tests (JAMF_TEST_WRITE=1 and INTUNE_TEST_WRITE=1)
npm run test:unit      # auth/roles unit tests only — no live JAMF/Intune credentials or network required
```

Start scripts use Bitwarden Secrets Manager — set `BWS_ACCESS_TOKEN` in your shell, then run `./start-jamf.sh` or `./start-intune.sh`. The `bws run --` wrapper injects credentials as env vars.

Tests require credentials as env vars (set by BWS or manually) plus `TEST_COMPUTER_NAME`, `TEST_COMPUTER_SERIAL`, and `TEST_USER_EMAIL` for JAMF test fixtures. The package/script/smart-group/policy/configuration-profile write tests (see Tests below) additionally read optional `TEST_PACKAGE_PATH`, `TEST_SCRIPT_NAME`, `TEST_SMART_GROUP_NAME`, `TEST_POLICY_NAME`, `TEST_CONFIG_PROFILE_NAME` — each test skips gracefully if its var is unset. The Intune test suite (`test/intune-api.test.ts`) needs no required fixtures for its read tests; its write tests optionally read `TEST_AZURE_GROUP_NAME`, `TEST_ANDROID_CONFIG_POLICY_NAME`, `TEST_ANDROID_SETTING_DEFINITION_ID`, `TEST_ANDROID_SETTING_VALUE`, and `TEST_ANDROID_APP_ID` — same skip-if-unset pattern.

## Architecture

Two standalone Streamable HTTP servers built on Express + `@modelcontextprotocol/sdk`. Each is single-file and self-contained — helpers like `toText`/`notFound`/`errorResult`/`resolveDevice` are duplicated per server rather than shared, so a fix in one server file does not propagate to the other:

- **`src/mcp/jamf-server.ts`** — JAMF MCP server on port 3001. `createJamfMcpServer(roles)` builds a fresh `McpServer` + `JamfClient` per HTTP request (stateless mode, required for load-balanced/APIM deployment), registering only the tools the caller's resolved roles permit; every POST to `/mcp` gets its own `StreamableHTTPServerTransport` with `sessionIdGenerator: undefined`, torn down on `res.on("close")`. Exposes read tools plus write tools (`jamf_update_computer`, `jamf_assign_computers_to_prestage`, `jamf_flush_mdm_commands`, `jamf_flush_policy_logs`, `jamf_create_configuration_profile`).
- **`src/mcp/intune-server.ts`** — Intune MCP server on port 3002. Same per-request stateless transport pattern. Exposes read tools plus write tools (`intune_send_device_action`, `intune_set_device_category`, `intune_set_device_name`, `intune_set_autopilot_group_tag`, `intune_assign_policy`, `intune_assign_app`, `intune_create_win32_app`, `intune_assign_app_to_groups`, `intune_create_android_compliance_policy`, `intune_update_compliance_policy`, `intune_assign_compliance_policy`, `intune_create_android_configuration_profile`, `intune_update_configuration_profile`, `intune_create_android_app_configuration_policy`, `intune_update_app_configuration_policy`, `intune_assign_app_configuration_policy`).

Both expose `GET /health` for load balancer checks and `GET /metrics` for Prometheus scraping, and return 405 on `GET`/`DELETE /mcp` (stateless servers don't support session resumption). MCP endpoints: `http://localhost:3001/mcp` (JAMF) / `http://localhost:3002/mcp` (Intune)

Both require `Authorization: Bearer <token>` on `/mcp` (not on `/health`), enforced by the shared `src/utils/auth.ts` `requireMcpAuth(options)` middleware — one of three intentionally-shared modules (alongside `src/utils/entra-jwt.ts` and `src/utils/roles.ts`), since duplicating auth/role logic risks the two servers' copies drifting out of sync. `requireMcpAuth` supports EITHER of two independent auth modes on the same request, though only one is enabled in production as of 2026-07-15:
1. A static bearer token from `JAMF_MCP_AUTH_TOKEN`/`INTUNE_MCP_AUTH_TOKEN` (comma-separated to allow rotation) — the original mechanism from before Entra auth existed. **Retired in production** on 2026-07-15 once Entra OAuth was confirmed working end-to-end and no non-interactive client (n8n, scripts) was found depending on it — `IAC/ansible-servers/linux/apps/desktop-management-mcp.yml` now renders both env vars empty, so prod no longer accepts these tokens even though the code path still exists. Still used by local dev (`start-jamf.sh`/`start-intune.sh` pull the real BWS secret directly, bypassing the ansible-rendered env file) since doing an interactive Entra flow locally isn't worth the hassle for that. Grants that server's full role set (see below) when present.
2. When `ENTRA_OAUTH_ENABLED=true`, an Entra-issued JWT verified against Entra's JWKS (`src/utils/entra-jwt.ts`, using `jose`) — tool visibility is then driven by the token's `roles` claim. This is the sole auth mode in production now.

Fails closed exactly as before: if neither mode is configured for a server, every `/mcp` request gets `503`.

### Metrics

Both servers expose `GET /metrics` (Prometheus text format) via `src/utils/metrics.ts` — a fourth intentionally-shared module alongside `auth.ts`/`entra-jwt.ts`/`roles.ts`, so metric names/labels can't drift between the two server copies. It exports a `prom-client` `Registry` (with `client.collectDefaultMetrics` registered), a `metricsMiddleware(req, res, next)` Express middleware mounted via `app.use(metricsMiddleware)` right after `app.use(express.json())` (before any routes, so it also covers `/health` and `/metrics` itself), and a `metricsHandler(req, res)` route handler wired as `app.get("/metrics", metricsHandler)`. Like `/health`, `/metrics` sits outside `requireMcpAuth` (only mounted on `/mcp`) — both servers are loopback-bound in production and fronted by Caddy, so this is intentionally open the same way `/health` already is.

Metric names/labels are kept identical to the sibling `jamf-prestage-tool` repo's `server/metrics.ts` on purpose, so the same Grafana dashboards/alerts work unmodified across both apps:
- `http_requests_total` / `http_request_duration_seconds` (Counter/Histogram, labels `method`/`route`/`status`, duration buckets `[0.01, 0.05, 0.1, 0.3, 0.5, 1, 2, 5, 10]`) — inbound requests, recorded by `metricsMiddleware` off `res.on("finish")`. `route` is just `req.path` rather than a normalized route pattern: each server only ever serves `/mcp`, `/health`, `/metrics` (plus the Entra OAuth protected-resource metadata paths when `ENTRA_OAUTH_ENABLED=true`), so there's no per-request identifier (serial number, device ID, etc.) that could leak into the label and blow up cardinality.
- `external_api_request_duration_seconds` / `external_api_errors_total` (Histogram/Counter, labels `target`/`method`/`status`, duration buckets `[0.05, 0.1, 0.3, 0.5, 1, 2, 5, 10]`) — outbound calls to JAMF Pro / Microsoft Graph. Recorded inside `logApiCall()` in `src/utils/logger.ts` rather than by instrumenting `JamfClient`'s axios instance or `IntuneClient`'s Graph SDK client directly — `logApiCall(logger, method, endpoint, statusCode, duration, error?)` is the one function both `jamf-api.ts` (72 call sites) and `graph-api.ts` (63 call sites) already funnel every outbound call's method/status/duration through, so hooking it required zero changes to either API client's ~135 individual call sites. `target` (`jamf`/`intune`) is derived from the `service` string each file already passes to `createLogger('jamf-api')`/`createLogger('intune-api')`, exposed as a `logger.service` field read back inside `logApiCall`. **Fixed 2026-07-29:** `jamf-api.ts`'s `catch` blocks previously never called `logApiCall` with an `error` argument (only `this.logger.error(...)`), so `external_api_errors_total` only incremented from JAMF's rare non-2xx-but-still-logged paths, not most thrown errors. All ~86 genuine HTTP-call catch blocks now also call `logApiCall(this.logger, method, endpoint, undefined, undefined, error as Error)` right after the existing `this.logger.error(...)`, matching the pattern `graph-api.ts` already used in several (not all) of its own error paths. A handful of catch blocks were deliberately left as-is: `authenticate()`/`ensurePlatformAuthenticated()` (auth-flow failures already tracked via `logAuth`), and one plain input-validation throw in `getComputersByUserIdentifier()` that fires before any HTTP call is made. `endpoint` here is log-only, not a Prometheus label (only `target`/`method`/`status` are labels) — a few call sites where the real resolved ID isn't in scope inside the `catch` block (it was `const`-declared inside the `try`) log the caller's original name/serial identifier instead, which is accurate enough for a human reading the log line.
- `mcp_tool_calls_total` (Counter, labels `server`/`tool`/`status`/`caller`) / `mcp_tool_call_duration_seconds` (Histogram, labels `server`/`tool`/`status`, same duration buckets as `http_request_duration_seconds`) — per-tool-call volume, success rate, latency, and caller attribution, one level below `http_requests_total` (which only sees one `POST /mcp` per call regardless of which tool it invoked or whether the tool itself failed). Recorded by `instrumentToolCalls(server, serverLabel, caller)`, called once from each of `createJamfMcpServer`/`createIntuneMcpServer` right after constructing the `McpServer` and before any `registerTool()` calls — it monkey-patches `server.registerTool` itself so every tool registered afterward is wrapped automatically, rather than editing each of the ~113 individual `registerTool()` call sites across both files. `status` is `"error"` when the handler throws *or* when it returns normally with `isError: true` (every tool here catches its own errors internally and returns the latter shape — see `errorResult()` — so both paths have to be checked). `caller` is resolved once per request in each server's `POST /mcp` handler as `req.auth?.extra.upn ?? req.auth?.clientId ?? "unknown"` — the signed-in user's UPN for Entra-authenticated callers, else the app's `clientId`, else the literal `"static-token"` for the legacy auth path (which has no per-caller identity). `caller` is deliberately omitted from the duration histogram to keep it low-cardinality (tool × status is the useful axis for spotting a slow tool; who called it matters for volume/attribution, not latency).

### Authentication and roles

Role names are Entra App Roles defined on one shared "Desktop Management MCP" resource app registration: `Jamf.Read`, `Jamf.Write`, `Intune.Read`, `Intune.Write` (`src/utils/roles.ts`). Each server only inspects its own role names via `hasRole()`/`resolveRolesFromAuthInfo()` and ignores the rest — there's no isolation lost by sharing one resource app, since role *assignment* (who gets which role) is still granted per-role, per-user/group in Entra independently. `Intune.Write` was added 2026-07-23 alongside the first Intune write tools (Win32 app publishing/assignment landed in one change; device actions, category, Autopilot group tag, and policy/app-by-name assignment landed in a parallel one). It was registered as an App Role on the Entra "Desktop Management MCP" app registration and first assigned to a tester (rcobb@colgate.edu) on 2026-07-24 — until an Entra-authenticated caller has this assignment, all eight Intune write tools are unreachable for them (the registration-time `hasRole()` gate means the tools are never registered on that request's `McpServer`, not just hidden), even though the static-token auth path already grants it automatically like every other role, per `resolveRolesFromAuthInfo`'s static-token-gets-everything behavior. Assign further testers via `POST /users/{userId}/appRoleAssignments` (Graph API) with `resourceId` set to the "Desktop Management MCP" service principal's object ID and `appRoleId` set to `Intune.Write`'s role ID (both `az ad sp show`/`az ad app show` lookups, not stored anywhere in this repo) — a client already holding a valid Entra token needs to re-authenticate (e.g. re-run the OAuth flow, or wait for `mcp-remote`'s token refresh) before the new roles claim takes effect.

Both `createJamfMcpServer(roles)` / `createIntuneMcpServer(roles)` take the caller's resolved role array and wrap each `server.registerTool(...)` call in `if (hasRole(roles, ...))` — a tool a caller's role doesn't grant is never registered on that request's `McpServer`, so it's simply not callable (not just hidden). The write/mutating JAMF tools (`jamf_update_computer`, `jamf_assign_computers_to_prestage`, `jamf_upsert_inventory_preload_record`, `jamf_flush_mdm_commands`, `jamf_flush_policy_logs`, `jamf_create_configuration_profile`, `jamf_create_script`, `jamf_upload_package`, `jamf_create_smart_group`/`jamf_create_smart_group_v2`, `jamf_create_user_group`, `jamf_create_policy`, `jamf_update_policy`, `jamf_upload_policy_icon`, `jamf_import_directory_user`, `jamf_create_disk_encryption_configuration`, `jamf_create_app_installer_deployment`, `jamf_update_app_installer_deployment`) and the Intune write/mutating tools (`intune_send_device_action`, `intune_set_device_category`, `intune_set_device_name`, `intune_set_autopilot_group_tag`, `intune_assign_policy`, `intune_assign_app`, `intune_create_win32_app`, `intune_assign_app_to_groups`, `intune_create_android_compliance_policy`, `intune_update_compliance_policy`, `intune_assign_compliance_policy`, `intune_create_android_configuration_profile`, `intune_update_configuration_profile`, `intune_create_android_app_configuration_policy`, `intune_update_app_configuration_policy`, `intune_assign_app_configuration_policy`) additionally call `assertRole(roles, JAMF_WRITE)`/`assertRole(roles, INTUNE_WRITE)` inside their own handler as a defense-in-depth check against a future refactor accidentally omitting the registration-time gate. All other tools rely solely on the registration-time gate.

`jamf_create_script`/`jamf_upload_package`/`jamf_create_smart_group` are upserts keyed by name — re-running with the same name updates the existing object in place rather than creating a duplicate (the yearly Office/MATLAB/Adobe re-publish case). `jamf_create_policy` always creates a new policy (no upsert); `jamf_update_policy` handles the enable/disable + scope-widen/narrow workflow for an existing one. Confirmed live that Classic API PUT on policies is a **partial merge**, matching `updateComputerRecord`'s established behavior — `updatePolicyScope` reads the current policy (to merge target/exclusion group names correctly) but sends back only `general.enabled` (if changing) and `scope` in the write body, not the full object. This isn't just an optimization: echoing the *entire* current policy back (the original design) actively broke — Jamf returns several sections on GET (`printers` being the one confirmed live) that trigger a `409 Conflict` ("Problem with printer") when resubmitted verbatim on PUT. Policy/smart-group writes go to Classic API (`/JSSResource/policies`, `/JSSResource/computergroups`) as hand-built XML — confirmed live that these two endpoints reject JSON bodies with `415`, unlike `/JSSResource/computers` (used by `updateComputerRecord`), which does accept JSON. The small XML serializer lives in `jamf-api.ts` (`buildXmlDocument`/`serializeXmlObjectBody`) rather than pulling in an XML library.

**Also confirmed live:** `getSmartComputerGroups()` previously had no pagination at all, silently truncating to the API's default page (100) with no signal more existed — a tenant with >100 smart groups (this one has 125) meant any name-based lookup (`resolveComputerGroupIdByName`, `jamf_create_policy`'s group scoping, `jamf_create_smart_group`'s upsert-exists check) could silently miss a real group. Fixed to page through the full result set the same way `listManagedDevices`/`listMobileDevices` do. Separately, creating (or updating) a smart group and immediately referencing it by name in a new policy can race against Jamf's internal indexing — confirmed live as a transient `409` that resolved itself on retry a few seconds later, not a code bug. If chaining `jamf_create_smart_group` → `jamf_create_policy`/`jamf_update_policy` in one automated flow, expect to retry once on a `409` referencing a just-created group.

**Known permission gap (as of 2026-07-15):** the JAMF API client's role has Create/Update but not Delete for Scripts, Policies, or Smart Computer Groups (confirmed live — every delete attempt returned 401/403). Package deletion does work. No `jamf_delete_*` MCP tools are exposed for any of these — deletion (when needed) is a manual admin action in the JAMF Pro UI.

**`jamf_send_mdm_command` was retired 2026-07-27 — infeasible via this API client's OAuth client-credentials auth, not a per-command privilege gap.** Originally suspected (per a since-superseded finding) to be a single missing privilege blocking just `RotateFileVaultKey`. Live testing disproved that: four different commands (`RotateFileVaultKey`, `UpdateInventory`, `EnableRemoteDesktop`, `BlankPush`) against two different, actively-checked-in, fully-managed Macs all failed — the first three identically, with a generic servlet-container "Unauthorized"/"The request requires user authentication" HTML page (not a Jamf JSON error), and `BlankPush` with a bare 500. That generic HTML response is the tell: it's being rejected before Jamf's own authorization logic runs at all, unlike every other privilege-denied case in this codebase (which always comes back as a clean Jamf JSON error body). Working theory, not yet confirmed: `/JSSResource/computercommands/` may require Basic Auth tied to a real Jamf Pro user account rather than an API-only OAuth client, since MDM commands are typically attributed to a human admin for audit purposes in Jamf's data model. Confirming that (and deciding whether to add a second, Basic-Auth credential path to `JamfClient` for just this one sub-resource) is a deliberate follow-up, not something to build speculatively. The tool, its `sendComputerMdmCommand` client method, and its two write tests were removed entirely rather than left registered-but-always-failing.

`jamf_flush_policy_logs`/`flushPolicyLogs` (added 2026-07-28) flushes a policy's execution history via `DELETE /JSSResource/logflush/policy/id/{id}/interval/{interval}`, making a "once per computer" frequency policy eligible to re-run on every computer in its scope. Deliberately flushes ALL computers scoped to the policy rather than accepting a specific one: the alternative XML-body `/JSSResource/logflush` endpoint takes both a `log_id` and a `<computers>` list, but the `log_id` filter is reported to be ignored when a computers list is also given, silently flushing that computer's history for every policy instead of just the one requested — not worth the risk of wiping unrelated policy history to avoid it. This is a destructive, irreversible, fleet-wide action (`destructiveHint: true`) — deliberately marked that way, unlike the more contained `jamf_flush_mdm_commands` (which only clears a stuck command queue, not historical audit records). **Confirmed live (2026-07-28)** against policy 3381 ("BeyondTrust Jump Client - Bernstein (Mac)", scoped to 8 computers via the "Classrooms - Bernstein" smart group): `interval="Zero Day"` works as-is, the endpoint returns `201` on success (not `204`), and a before/after check of 5 sampled scoped computers' policy logs (via `jamf_get_computer_policy_logs`) confirmed each went from 1 log entry for this policy to 0 — the flush verifiably took effect, not just that the call returned success. The other `interval` enum values (`One Day Away`, `One Week Away`, etc.) are documented by the same Classic API resource but have not themselves been exercised live.

`jamf_assign_computers_to_prestage`/`assignSerialsToPrestage` add serials to a prestage's scope one at a time via `POST /api/v2/computer-prestages/{id}/scope`, rather than a single `PUT` with the whole merged serial list — confirmed live (found reconciling PreStage scope after a bulk-unassignment incident, see the `DesktopManagementContext` repo's `scripts/reassign-prestage-scope.sh`) that Jamf's v2 scope endpoint's `POST` verb adds one serial independently, validating each one separately, unlike `PUT` (a full-replace) which 400s the *entire* batch with no per-serial detail if even one serial fails Jamf's server-side ADE validation — most commonly `DEVICE_DOES_NOT_EXIST_ON_TOKEN` (the serial's Apple Business Manager assignment has moved off this MDM server's token, an ABM-side state, not a Jamf or tool bug). The tool result's `failed` array reports each rejected serial with Jamf's real per-serial error detail (parsed from the v2 API's `{"errors": [{"code": ..., "description": ...}]}` error body via `extractJamfErrorDetail`) rather than a bare status code; `success: true` only means zero serials failed, so check `failed` rather than assuming success from a non-thrown result.

`jamf_list_policies` gained `categoryName` (server-side filtered via the Classic API's `/JSSResource/policies/category/{category}` endpoint) and `excludeAutoGeneratedNames` (client-side regex excluding legacy imaging-era policies named like `"2014-05-27 at 1:47 PM | akhazaee | 1 Computer"`) params — both free narrowing mechanisms, since the plain `/JSSResource/policies` bulk-list endpoint returns only `id`/`name` with no other fields and no query-param filtering at all. `jamf_list_self_service_policies` is a new tool for the harder case (filtering to policies with `self_service.use_for_self_service: true`, which isn't present in the bulk list and isn't filterable server-side): it narrows via the two free mechanisms above first, then hydrates each remaining candidate individually via `getPolicyDetail`, capped at `maxDetailChecks` (default 300, since hydrating the full ~2,724-policy fleet one-by-one isn't practical in a single call) — the result's `droppedCount` reports how many narrowed-down candidates were left unchecked rather than silently truncating. `jamf_get_policy`'s markdown output now also surfaces the Self Service icon status (present/filename or "None").

`jamf_get_computer_policy_logs` (added 2026-07-28) surfaces a single computer's policy execution history — JAMF Pro's computer History > Policy Logs view — via the Classic API's `Policy_Logs` subset of `/JSSResource/computerhistory` (Classic-API-only, no v1/v3 equivalent). **Confirmed live:** the subset name needs the underscore (`Policy_Logs`, not `PolicyLogs`) — an invalid subset silently returns an empty object rather than erroring, so this was verified against a real computer (71 log entries) rather than assumed from docs. Also confirmed live: JAMF returns entries in an arbitrary order, not sorted by date, so `getComputerPolicyLogs` always sorts by `date_completed_epoch` descending before applying the optional `policyName`/`status` filters and `limit` (default 100) — check `summary.truncated` rather than assuming `logs` is the complete set. Resolves the computer via the existing `resolveComputerId` helper (name or serial), same as `updateComputerRecord`/`getFilevaultStatus`. The actual fetch/sort/filter logic lives in a private `fetchPolicyLogsForComputerId(computerId, options)`, reused by `jamf_get_policy_fleet_status` below against computer IDs it already has (skipping `resolveComputerId`'s extra lookup).

`jamf_get_policy_fleet_status` (added 2026-07-28) answers the harder, heavier question `jamf_get_computer_policy_logs` can't: "is this policy actually rolling out / failing fleet-wide?" It resolves a policy's scope (`scope.computers` plus `scope.computer_groups`, minus `scope.exclusions`) into a deduplicated computer set, then checks each one's most recent run of that specific policy via `fetchPolicyLogsForComputerId` with an exact `policyId` filter (added alongside this — more precise than the existing `policyName` substring filter, which could ambiguously match a renamed or similarly-named policy). **Confirmed live:** `getSmartGroupDetail` (already used by `jamf_get_smart_group`) embeds the current `computers` array (id/name/serial) in its Classic API response for smart groups, so no separate group-membership call is needed to resolve `scope.computer_groups` — same call should work structurally for static groups too (shared endpoint), though this tenant has zero static groups today so that specific path is unverified. Policies scoped to All Computers are refused outright (`allComputers: true`, empty result) rather than enumerated — checking a 1000+ computer fleet one-by-one isn't practical as a single call. Sequential per-computer history fetches (not parallel), matching `listSelfServicePolicies`'s existing convention of not hammering JAMF with concurrent requests; `maxComputers` (default 100) caps how many scoped computers get checked, `droppedCount` reports the remainder. **Known simplification, not a bug:** `scope.limitations` (network segments, LDAP users/groups) are not resolved — those narrow scope based on session context rather than a static computer list, so they can't be cheaply cross-referenced the way direct computers/groups can; a computer matched via `scope.computers`/`scope.computer_groups` might still be excluded by a limitation in ways this result won't reflect.

`jamf_upload_policy_icon` uploads a Self Service icon image to a policy via `POST /JSSResource/fileuploads/policies/id/{id}`, confirmed live (2026-07-24, 8 policies) with the image as a multipart field named **`name`** (not `file` — Classic API's fileuploads endpoint uses that field name regardless of what's being uploaded), using native `fetch`/`FormData` rather than axios (same reason as `uploadPackageFileBuffer`: axios's Node adapter doesn't cleanly multipart-encode a plain `FormData` without the extra `form-data` package). One upload during that session hit the exact "201 but silently no-op'd" pattern already known from policy list/scope writes (`self_service_icon` stayed empty on a follow-up GET despite the 201) — a short OAuth token TTL was a suspected but unconfirmed contributing factor. The tool always verifies with a GET after uploading and retries once automatically before reporting failure; check `success`/`retried` in the result rather than assuming the call worked just because it didn't throw.

**Jamf Platform API Gateway (`JAMF_PLATFORM_*` env vars) — confirmed live 2026-07-29 with a real account.jamf.com Integration credential.** Originally added for three tool groups (`jamf_list_filevault_status`, the `jamf_*_compliance_*` tools, and the `jamf_*_blueprint*` tools) that hit Jamf's shared **platform-api Gateway** (`https://{region}.apigw.jamf.com/api/...`, region defaulting to `"us"`, overridable via `JAMF_PLATFORM_REGION`) rather than this tenant's own `JAMF_URL` — a genuinely different host *and* a genuinely different OAuth2 client-credentials pair (`JAMF_PLATFORM_CLIENT_ID`/`JAMF_PLATFORM_CLIENT_SECRET`, exchanged at `JAMF_PLATFORM_URL`) from `JAMF_CLIENT_ID`/`JAMF_CLIENT_SECRET`. `JamfClient` authenticates this credential independently via `ensurePlatformAuthenticated()` (its own token cache, 900s TTL per a live response, same 60s-buffer lazy-refresh pattern as the main `ensureAuthenticated()`) against a second axios instance (`platformClient`) — it does **not** reuse the main tenant token, which was the original (broken) assumption before real credentials existed. One important surprise: the real deployed token endpoint (`https://us.apigw.jamf.com/auth/token`, confirmed live) does **not** match what Jamf's own OpenAPI spec documents (`/oauth2/token`, which 404s) — `JAMF_PLATFORM_URL` must be the real value from the Integration's own details panel, not derived from the spec.

**What this credential can and cannot do — confirmed 2026-07-29 to be far broader than first assumed.** The initial finding (bulk FileVault working through the Gateway while 403ing directly) looked like a narrow, specific grant. Direct testing of every other non-Classic REST resource this file uses proved otherwise: **computers-inventory (+ detail), categories, departments, sites, scripts, packages, computer-groups (+ smart-group-membership), mobile-devices (+ detail), computer-prestages (+ scope), app-installers, cloud-idp, and inventory-preload all return real data through this Gateway credential** — essentially the entire non-Classic Jamf Pro REST surface. The only two confirmed exceptions: Classic API (`GET .../api/proclassic/JSSResource/categories` → clean `403 BAD_PERMISSIONS`) and `patch-policies` specifically (`GET .../api/pro/v3/tenant/{id}/patch-policies` → `403`, unlike every sibling v3 resource). **Given that breadth, `restGet()` (private, in `jamf-api.ts`) is now the shared entry point for every non-Classic REST GET in this file** — it routes through the Gateway (via `toGatewayProPath()`, which maps a direct path like `/api/v3/computers-inventory` to `/pro/v3/tenant/{tenantId}/computers-inventory`) whenever `JAMF_PLATFORM_*` is configured, and transparently falls back to the direct client otherwise — a static per-call decision based on config presence (not a try-then-catch-on-error fallback, which would risk silently masking a genuinely broken Gateway credential as "just fall back"). Confirmed live in both directions: with the Gateway configured, `ensurePlatformAuthenticated()`'s log line fires and calls succeed via the Gateway; without it, the same calls succeed via the direct client exactly as before — zero behavior change for a deployment that hasn't been given `JAMF_PLATFORM_*`. **Still direct-client-only, deliberately:** all Classic API calls (obviously — no Gateway access at all), `patch-policies` (confirmed 403 via Gateway), `jamf_whoami`'s `/api/v1/auth` call (its whole purpose is reporting the *direct* client's own privileges, not the Gateway's), and every POST/PUT/DELETE (write) in this file — only GETs were migrated; write-path Gateway parity has not been tested and would need its own deliberate verification before relying on it.

**Intune write tools (added 2026-07-23):** `intune_send_device_action` wraps five Graph remote actions (`syncDevice`, `rebootNow`, `remoteLock`, `retire`, `wipe`) behind one command enum — retire and wipe are irreversible (retire unenrolls and removes company data; wipe factory-resets). That single permission gated **all five** `intune_send_device_action` commands *and* `intune_set_device_name`'s `setDeviceName` action. `intune_set_device_category` assigns an existing device category to a device — confirmed live that **neither** documented approach actually works against this tenant: `deviceCategory@odata.bind` on `PATCH /managedDevices/{id}` is rejected outright ("Bind requests not supported for containment navigation property"), and Microsoft's own docs' fallback form, `PATCH .../managedDevices/{id}/deviceCategory` (also the form a still-open `msgraph-sdk-powershell` issue reports failing), 404s with an empty body. Categories themselves must already exist (no write API for creating them is exposed here, matching the "portal-only" pattern already established for JAMF buildings/departments).

`intune_set_autopilot_group_tag` resolves serial → Autopilot device identity ID the same way `getAutopilotProfileStatus` already does, then calls `updateDeviceProperties` — confirmed live with a set-then-revert on a real Autopilot-registered device. Note: the write returns 204 immediately but the change can take ~10-15s to actually show up on a subsequent read (confirmed live) — Autopilot's service has its own eventual-consistency lag independent of Graph's usual read-after-write behavior, so don't treat an immediately-stale read as a failed write.

**Two tools exist for app assignment, deliberately kept separate rather than merged into one:** `intune_assign_app_to_groups` takes the caller's full desired `{groupId, intent}[]` list and posts it verbatim — a thin, literal wrapper around Graph's actual replace-the-whole-set `/assign` semantics, correct for bulk/scripted rollouts where the caller already tracks the complete assignment set. `intune_assign_app` takes a single group (by name or GUID) plus intent and does its own read-modify-write internally to preserve every other group's existing assignment — friendlier for the common "just add/move this one group" case, at the cost of an extra read round-trip. Same tradeoff applies to `intune_assign_policy`, which has no `_to_groups`-style sibling (no bulk config-policy assignment tool exists yet).

`intune_assign_policy`/`intune_assign_app` add or move a single group's assignment on a configuration policy or app deployment. Unlike JAMF's Classic API PUT (confirmed live as a partial merge, see above), **Graph's `/assign` action fully replaces the assignment collection** rather than appending to it — confirmed live, not just read from docs. Both client methods therefore always do their own read-modify-write: GET current assignments, drop any existing entry for the same group, append the new entry, then POST the whole array back to `/assign`. **Confirmed live and fixed:** assignments can carry `source: "policySets"` when the policy/app belongs to an Intune Policy Set — echoing one of those back through `/assign` does NOT get recognized as "the same assignment already there"; it silently creates a *second*, independent `direct` assignment for that group, duplicating scope the Policy Set already grants. (Caught this live against a real Policy-Set-linked policy — the first test run left a stray duplicate direct assignment in production, which had to be manually cleaned up by re-posting the correct set.) Fixed by retaining only `source: "direct"` assignments (or ones with no `source` field at all, as classic `deviceConfigurations` assignments have) when rebuilding the array — the `policySets` entry regenerates itself automatically on the next read regardless, so it must never be included in what gets posted back. Existing retained assignments are also passed through a `sanitizeAssignmentTarget()` helper that keeps only `@odata.type`/`groupId`/`collectionId`/filter fields rather than the full GET response, as a precaution against the same class of bug JAMF's policy PUT hit (echoing an entire GET body back on write triggering a 409 from a field the API didn't expect on write) — that specific failure mode hasn't been observed on the Intune side, this is a preventive measure taken given the JAMF precedent.

**Android config profile and compliance tooling (added 2026-07-28):** this tenant's Android config profiles are 100% Settings Catalog (`platforms: "androidEnterprise"`, `technologies: "android"`) — zero classic `androidGeneralDeviceConfiguration`/`androidWorkProfile*`/`androidDeviceOwner*` objects exist here, so config profile create/update targets Settings Catalog rather than the legacy classic Android types. **Confirmed live and fixed:** `getConfigurationPolicies` previously treated Graph's `platforms`/`technologies` fields as arrays, but Graph actually returns them as a single string for Settings Catalog policies (e.g. `"androidEnterprise"`, `"mdm,endpointPrivilegeManagement"`) — `Array.isArray(policy.platforms)` was always false, so every settings-catalog policy silently normalized to `platforms: []` and platform filtering matched nothing. A second, independent bug compounded it: `intune-server.ts`'s markdown renderer read `p.platform` (singular) when the actual normalized field is `platforms` (plural), so the "Platform:" column always showed `—` even once the first bug was fixed. Both are fixed now (`platforms`/`technologies` kept as raw strings, filter does a substring match on the string, renderer reads the correct field name).

`intune_get_configuration_profile` reads a single policy's full detail — for classic device configurations, one GET already returns every type-specific property inline (it's a single polymorphic resource); for Settings Catalog, metadata plus the settings array via a separate `GET .../configurationPolicies/{id}/settings` call (`getConfigurationPolicySettings`), since Settings Catalog doesn't embed its settings in the metadata GET. **Confirmed live, and a real limitation worth knowing about:** both the metadata GET and the `/settings` GET for this tenant's actual Android Enterprise Settings Catalog policies (`Allow Google Accounts`, `Allow Google Accounts - BYOD`) consistently 500 via a Microsoft-internal backend proxy (`DeviceConfigV2/DCV2GraphService`, a generic non-JSON "An error has occurred" error body) — reproduced repeatedly, not transient, and this app registration's bulk list call for configuration policies silently omits both from its results too rather than erroring the whole list. Other Settings Catalog platforms (Windows, macOS) in this tenant are unaffected. This appears to be a Microsoft-side issue specific to reading Android Enterprise Settings Catalog policies via this app registration/tenant combination — not something this client's request construction can work around. Treat `intune_get_configuration_profile`/`intune_list_configuration_policies` as unreliable for this tenant's *existing* Android Settings Catalog policies until Microsoft support or a permission change resolves it; newly-created ones (via `intune_create_android_configuration_profile`) may or may not hit the same issue — untested, since creating a live test policy wasn't done as part of this change (see Tests below).

`intune_create_android_configuration_profile`/`intune_update_configuration_profile` (Settings Catalog) take a raw passthrough `settings` array of Graph `settingInstance` objects rather than a modeled schema — Microsoft's Settings Catalog has hundreds of Android setting definitions per platform, and mirroring Graph's own property names directly (the same approach `jamf_upsert_inventory_preload_record`-style tools don't need, since JAMF has no equivalent settings-catalog complexity) avoids reinventing that schema. The intended workflow is reading an existing similar policy via `intune_get_configuration_profile` (`response_format="json"`) and using its `settings` array as a copy-and-modify template. **Not yet confirmed live:** the exact Settings Catalog policy update mechanism for the `settings` array (`updateSettingsCatalogPolicy` PATCHes the policy resource with the full replacement array — Settings Catalog settings aren't a separately-addressable sub-resource for writes) — verify against a real update before relying on it.

**Fleet-visibility and bug-fix tools added 2026-07-28** (closing several `MCP_TOOL_GAPS.md` entries from the `DesktopManagementContext` repo): `intune_list_autopilot_devices` bulk-lists Windows Autopilot device identities — confirmed live against this tenant (1,451 real devices) after fixing a real bug found in the process: a `.select()` on this beta endpoint 500s ("An internal server error has occurred") in this tenant, the same failure class already known for `getAutopilotProfileStatus`'s fallback path, so the bulk method deliberately omits `.select()` and filters client-side instead. `ownerType` (Personal/Corporate) was added to `intune_list_devices`/`intune_get_device_by_name`/`intune_get_device_by_serial`/`intune_get_devices_by_user`'s output, with a fleet-wide breakdown and filter on `intune_list_devices`. `intune_troubleshoot_policy` and `intune_troubleshoot_app`'s markdown formatters both had the same bug — template-interpolating `findings`/`recommendations` objects directly instead of destructuring `{severity, code, message}`/`{priority, action, details}` fields, producing literal `[object Object]` per entry — now fixed in both. `intune_list_enrollment_restrictions` (wrapping `deviceManagement/deviceEnrollmentConfigurations`) is confirmed live and working with no permission gap (8 real configs returned). `intune_list_conditional_access_policies` (wrapping `identity/conditionalAccess/policies`) is added but confirmed-live 403s with "required scopes are missing in the token" — this app registration needs the `Policy.Read.All` Graph application permission granted and admin-consented before it returns data; since auth uses the `.default` scope (see `authScopes` in `graph-api.ts`), no code change will be needed once that grant lands.

**Entra ID does not support OAuth Dynamic Client Registration (RFC 7591)**, which real MCP clients lean on for zero-config setup — this project deliberately does NOT implement a custom OAuth broker/proxy to paper over that gap (see the plan history for the phased rationale); it's a resource-server-only integration. Practical per-client setup, confirmed by live testing (not just read from docs):
- **OpenCode** — works today: register a small native/public Entra client app (PKCE, no secret) and configure it as `oauth.clientId` in `opencode.json`, with an explicit `oauth.scope` (Entra's `/authorize` requires a non-empty `scope`; OpenCode doesn't infer one). `opencode mcp auth <name>` drives a normal browser PKCE flow.
- **Codex CLI** — no static-`clientId` OAuth support upstream yet; keep using `bearer_token_env_var` pointing at the existing static token. Not tied to per-user Entra identity in this phase.
- **Claude Code** — its *native* HTTP-transport OAuth (`claude mcp add --transport http ... --client-id ... --callback-port ...`) sends no `scope` parameter at all and fails against Entra with `AADSTS900144: The request body must contain the following parameter: 'scope'` — confirmed live, not an assumption; there's no CLI flag to inject one. Use the `mcp-remote` npm package instead, as a stdio↔http bridge, with **both** `--static-oauth-client-info '{"client_id":"<public-client-id>"}'` and `--static-oauth-client-metadata '{"scope":"openid profile offline_access <resource-scope>"}'` (the metadata flag is required — client-info alone doesn't carry scope). Add it via `claude mcp add-json <name> '{"type":"stdio","command":"mcp-remote","args":["<mcp-url>","<fixed-port>","--static-oauth-client-info","...","--static-oauth-client-metadata","..."]}'`. Pin an explicit port (mcp-remote otherwise derives one from a hash of the server URL) and register its exact callback redirect URI (`http://localhost:<port>/oauth/callback` — note `localhost`, not `127.0.0.1`, and note the path differs from OpenCode's own `/mcp/oauth/callback`) on the Entra public client. Revisit if/when Claude Code's native flow gains scope support upstream.
  - **Headless boxes (no local browser to complete the callback)** — `mcp-remote` 0.1.38 only implements Authorization Code + PKCE with a localhost callback listener (confirmed by inspecting its published bundle: zero references to `device_code` anywhere in `dist/*.js`), so its normal flow needs either a browser on the same machine or SSH port-forwarding the callback port from a client machine that has one. `src/cli/entra-device-auth.ts` is a from-scratch implementation of Entra's OAuth 2.0 Device Authorization Grant (RFC 8628) against the same public client app mcp-remote already uses (`isFallbackPublicClient: true`, confirmed via `az ad app show` — no Entra-side changes needed, since device code doesn't use a redirect URI at all) as an alternative that needs no local listener: `login` prints a `https://microsoft.com/devicelogin`-style URL + short code to complete on any device, `token` prints a valid access token (refreshing via the cached `refresh_token` if near expiry), `status` shows the cached token's roles/expiry without printing the token itself. Tokens cache to `~/.mcp-auth/entra-device/<profile>.json`. `login` still needs to be run interactively once per profile before any of this works.
  - **Keeping long-running sessions authenticated (added 2026-07-28) — `seed-mcp-remote` and `keepalive` subcommands.** The originally-documented approach — `entra-device-auth token` feeding a bare access token to `mcp-remote --header "Authorization:Bearer $TOKEN"` — has a real staleness problem: confirmed by reading `mcp-remote` 0.1.38's source directly, `--header` is parsed once at process startup into a fixed in-memory object and never re-read, so a long-running `mcp-remote` process (and the MCP client session riding on its stdio pipe) 401s on every request once that token expires (~60-90min), with no recovery short of restarting the client. `seed-mcp-remote --profile <name> --server-url <url>` fixes this by writing the profile's token/refresh_token directly into **mcp-remote's own** on-disk token cache (`~/.mcp-auth/mcp-remote-<version>/<hash>_tokens.json`, `<hash>` an MD5 of the bare server URL — confirmed live against this tenant's real cache directory, including that the bundled `version` constant baked into `mcp-remote`'s own code doesn't necessarily match its `package.json` version, e.g. `0.1.37` vs. the installed `0.1.38`, so the directory name can't be assumed and is resolved at runtime instead) in the exact shape its `OAuthTokensSchema` expects. Traced through `mcp-remote`'s source and confirmed: its Streamable HTTP transport calls `provider.tokens()` — a fresh disk read — on every single outgoing request (not just once at connection setup), and on a 401 it automatically refreshes via the SDK's standard `auth()` helper using the cached `refresh_token`, then **transparently retries the exact same request** (`return this.send(message)`) — no restart, no proxy, all built into the library already. Once seeded, invoke `mcp-remote` the same way the browser-capable (non-headless) setup already does — `--static-oauth-client-info`/`--static-oauth-client-metadata`, no `--header` at all — and it self-refreshes indefinitely via that same mechanism (see the updated `scripts/mcp-wrapper-device-auth.sh.example`). `keepalive --profile <name> --server-url <url> [--interval-seconds 1800]` wraps `seed-mcp-remote` in a loop for two reasons beyond what reactive refresh-on-401 alone covers: it avoids the one-request refresh-latency hit right at the expiry boundary, and it keeps a genuinely idle box's `refresh_token` exercised regularly so it can't go stale from disuse even with zero real MCP traffic — run it as a long-lived process (e.g. a `systemd --user` service) alongside the MCP client, one per profile.

**Multiple identifier URIs are required on the resource app**, one reason this took real testing to get right: any MCP-spec client that sends the RFC 8707 `resource` parameter (OpenCode and `mcp-remote` both do, using the literal MCP server URL taken from this project's own RFC 9728 protected-resource metadata) needs that exact URL registered as an `identifierUris` entry on the Entra app — Entra rejects the request with `AADSTS9010010` if `resource` and `scope` resolve to different app identities. Since jamf-mcp and intune-mcp are different URLs sharing one resource app, both `https://jamf-mcp.colgate.edu/mcp` and `https://intune-mcp.colgate.edu/mcp` are registered as additional identifier URIs alongside the abstract `api://colgate.edu/desktop-mgmt-mcp` one.

### API Clients

- `src/jamf/jamf-api.ts` — `JamfClient`: authenticates via OAuth2 client-credentials (`POST /api/v1/oauth/token`), caches the bearer token and re-authenticates lazily via `ensureAuthenticated()` once it's within 60s of `expires_in`. Uses JAMF Pro REST API v1/v3 for most endpoints (e.g. computer lookups go through `computers-inventory` to resolve an ID, then `computers-inventory-detail/:id` for the full record); falls back to the Classic API (XML-based, e.g. policies, configuration profiles) where v1/v3 doesn't cover a resource. Separately, `getFilevaultStatusBulk`/`getComplianceBaselines`/`getComplianceBenchmarks`/`getComplianceBenchmarkDetail`/`getComplianceBenchmarkDevices`/`getBlueprints`/`getBlueprintDetail`/`getBlueprintComponents` go through a second, independently-authenticated client (`platformClient`, via `ensurePlatformAuthenticated()`) pointed at the Jamf Platform API Gateway — see the Platform API Gateway section above for why this is a genuinely separate host and credential, not a variant of the main client.
- `src/intune/graph-api.ts` — `IntuneClient`: uses `@azure/identity` `ClientSecretCredential` + `@microsoft/microsoft-graph-client`'s `TokenCredentialAuthenticationProvider` (token acquisition/caching handled by the SDK, not manually). Mixes Graph API versions per-endpoint — e.g. Autopilot lookups try a `v1.0` server-side `$filter` first and fall back to fetching a `beta` batch and filtering client-side if the filter 500s. Write methods (`sendManagedDeviceAction`, `setDeviceCategory`, `setDeviceName`, `updateAutopilotGroupTag`, `assignConfigurationPolicyToGroup`, `assignAppToGroup`, plus the compliance-policy, configuration-profile, and app-configuration-policy write methods added 2026-07-28) live in a "Write operations" section at the bottom of the file; `resolveGroupId()` (private) resolves an Azure AD group by exact `displayName` or accepts a GUID directly, used by every assignment method. Compliance policies (`getCompliancePolicies`/`getCompliancePolicyDetail`/`createAndroidCompliancePolicy`/`updateAndroidCompliancePolicy`/`assignCompliancePolicyToGroup`) and app configuration policies (`getAppConfigurationPolicies`/`getAppConfigurationPolicyDetail`/`createAndroidAppConfigurationPolicy`/`updateAndroidAppConfigurationPolicy`/`assignAppConfigurationPolicyToGroup`) each get their own dedicated section — see the Android tooling paragraphs above for what's confirmed live vs. not. Each of these three write surfaces also has a test-only `delete*` method (`deleteCompliancePolicy`/`deleteConfigurationProfile`/`deleteAppConfigurationPolicy`) — not exposed as MCP tools (no delete tools exist anywhere in this codebase's MCP surface), used solely so `test/intune-api.test.ts` can self-clean objects it creates.

Both clients log via `src/utils/logger.ts`, a plain `console.*`-based structured logger (`createLogger(service)` + `logApiCall`/`logAuth` helpers) — the doc comment calling it "for Azure Functions" is a holdover from where this code was extracted from; there's no Azure Functions runtime here. `LOG_LEVEL=debug` enables debug-level output.

### Device/name resolution

Read tools that take a human name generally resolve it server-side rather than requiring an ID:
- Intune: `resolveDevice()` (in `intune-server.ts`) accepts `deviceName`, `deviceId`, or `serialNumber` and normalizes to `{ deviceId, azureADDeviceId }`. `resolveAppByName()`, `resolvePolicyByName()`, `resolveCompliancePolicyByName()`, and `resolveAppConfigurationPolicyByName()` all resolve human-readable names to GUIDs the same way: fetching the full list and matching case-insensitively (exact match preferred, first partial match as fallback).
- JAMF: several `JamfClient` methods (e.g. `getComputerByName`, `updateComputerRecord`, `assignSerialsToPrestage`) accept a name/serial and internally look up the JAMF numeric ID before calling the detail/write endpoint.

### Tool registration pattern

Tools are registered via `server.registerTool(name, schema, handler)` with Zod schemas and `annotations` (`readOnlyHint`, `openWorldHint`, `destructiveHint`) describing side effects. Handlers return `{ content: [{ type: "text", text }] }`, or `{ isError: true, content: [...] }` on failure/not-found. Nearly every read tool takes an optional `response_format: "markdown" | "json"` (default `"markdown"`) — the shared `toText(data, format, markdownFn)` helper either dumps raw JSON or renders a hand-built markdown summary, so adding a field to markdown output means also checking whether it should surface in the raw JSON path (it already does, since JSON mode returns the full API response object, not the trimmed markdown view).

## Environment Variables

**JAMF** (injected by BWS from `bws-secrets.map`):
- `JAMF_URL` — e.g. `https://yourorg.jamfcloud.com`
- `JAMF_CLIENT_ID`, `JAMF_CLIENT_SECRET`
- `JAMF_MCP_AUTH_TOKEN` — bearer token(s) MCP clients must present (comma-separated to allow rotation). Rendered empty in prod as of 2026-07-15 (retired in favor of Entra OAuth) — still set for local dev via `start-jamf.sh`.
- `JAMF_MCP_PUBLIC_URL` — this server's externally-visible origin, e.g. `https://jamf-mcp.colgate.edu` (required only when `ENTRA_OAUTH_ENABLED=true`)
- `JAMF_PACKAGE_UPLOAD_DIR` — directory `jamf_upload_package` is allowed to read files from on this server's own filesystem (not the MCP client's). Required for that tool; it fails closed (refuses every call) if unset, and rejects any `localFilePath` outside it.
- `JAMF_PLATFORM_CLIENT_ID`, `JAMF_PLATFORM_CLIENT_SECRET` — separate account.jamf.com Integration credential for the Jamf Platform API Gateway (not the same as `JAMF_CLIENT_ID`/`JAMF_CLIENT_SECRET`). Required only by `jamf_list_filevault_status`, the `jamf_*_compliance_*` tools, and the `jamf_*_blueprint*` tools — see the Platform API Gateway section above.
- `JAMF_PLATFORM_URL` — token endpoint for the above credential (real deployed value confirmed live, differs from what Jamf's OpenAPI spec documents)
- `JAMF_PLATFORM_TENANT_ID` — tenant UUID for the Platform API Gateway, distinct from `JAMF_URL`
- `JAMF_PLATFORM_REGION` — optional, Platform API Gateway region (`"us"` default, `"eu"`, `"apac"`)

**Intune** (injected by BWS from `bws-secrets.map`):
- `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` — Graph app-only client credentials for device data, unrelated to the Entra auth vars below
- `INTUNE_MCP_AUTH_TOKEN` — bearer token(s) MCP clients must present (comma-separated to allow rotation). Rendered empty in prod as of 2026-07-15 (retired in favor of Entra OAuth) — still set for local dev via `start-intune.sh`.
- `INTUNE_MCP_PUBLIC_URL` — this server's externally-visible origin, e.g. `https://intune-mcp.colgate.edu` (required only when `ENTRA_OAUTH_ENABLED=true`)

**Entra ID auth** (shared by both servers, each can enable independently; injected by BWS from `bws-secrets.map`):
- `ENTRA_OAUTH_ENABLED` — `"true"` to accept Entra-issued bearer tokens on `/mcp` in addition to the static token
- `ENTRA_TENANT_ID` — Entra tenant GUID (deliberately separate from `AZURE_TENANT_ID` above — different app registration, different purpose)
- `ENTRA_RESOURCE_APP_ID_URI` — Application ID URI of the "Desktop Management MCP" resource app, e.g. `api://colgate.edu/desktop-mgmt-mcp` (Entra tenants that require a verified domain in the URI, as Colgate's does, will reject a bare `api://desktop-mgmt-mcp` — confirmed live)
- `ENTRA_RESOURCE_APP_ID` — GUID app ID of the same resource app; accepted as an alternate `aud` value. MCP-spec clients that send the RFC 8707 `resource` parameter (e.g. OpenCode) get tokens audienced to this GUID rather than the URI above, even with `requestedAccessTokenVersion: 2` set on the app — confirmed against a real issued token, not assumed from docs.

## Tests

`test/jamf-api.test.ts` uses Node.js built-in `node:test` — no extra test framework. Tests are live integration tests against a real JAMF Pro API. Write operations are gated behind `JAMF_TEST_WRITE=1`. Tests that may fail due to API client permissions use `permissionAwareTest()` which treats 401/403/404 as a skip rather than a failure.

The script/smart-group/policy/configuration-profile upsert write tests deliberately do NOT create-then-delete (the API client can't delete those object types — see the permission gap noted above); each looks for a pre-existing, manually-created fixture by name (`TEST_SCRIPT_NAME`, `TEST_SMART_GROUP_NAME`, `TEST_POLICY_NAME`, `TEST_CONFIG_PROFILE_NAME` — all optional, test skips via `t.skip()` if unset or if no object with that name exists yet) and only exercises the update-in-place path. The package upsert test is fully self-cleaning instead (`TEST_PACKAGE_PATH`, also optional) since package delete permission is confirmed present.

The Compliance Benchmarks tests early-return (the `if (!first) return;` convention, not `t.skip()` — `permissionAwareTest()`'s wrapped function takes no `t` argument to call it with) whenever `JAMF_PLATFORM_TENANT_ID` is unset. As of 2026-07-29 real Platform API Gateway credentials exist and these run live in this environment (confirmed: real baselines catalog, empty-but-successful benchmarks list) — the early-return only matters for a dev/CI environment that hasn't been given the `JAMF_PLATFORM_*` credentials.

`test/auth.test.ts` covers `requireMcpAuth`'s dual-mode fallback/fail-closed behavior and the `roles.ts` helpers with fakes — no live credentials or network access needed, hence the separate `npm run test:unit` script.

`test/intune-api.test.ts` (added 2026-07-28) mirrors `jamf-api.test.ts`'s conventions against a real Intune tenant — write operations gated behind `INTUNE_TEST_WRITE=1`. `permissionAwareTest()` here also treats Graph's generic `DeviceConfigV2/DCV2GraphService` backend proxy failure ("An error has occurred", no structured error body) as a soft skip alongside 401/403/404, since that's a confirmed-live, repeatable failure mode for this tenant's real Android Settings Catalog policies specifically (see the Android tooling notes above) — broader than JAMF's equivalent helper needs to be. The compliance-policy and config-profile write tests are fully self-cleaning (create → update → assign → delete, using the test-only `delete*` client methods), gated on an optional `TEST_AZURE_GROUP_NAME` fixture (skips via `t.skip()` if unset). The config-profile write test additionally needs `TEST_ANDROID_SETTING_DEFINITION_ID` (and optional `TEST_ANDROID_SETTING_VALUE`) — a real Settings Catalog setting definition ID from this tenant's catalog — since no definition ID is hardcoded (guessing one that doesn't exist in this tenant's catalog version would fail for reasons unrelated to the code being tested). The OEMConfig write test needs `TEST_ANDROID_APP_ID` and stays skipped in this tenant today, since no Android app exists in the Intune catalog to target (see the OEMConfig note above).

## Deployment

Both servers run in production as Podman quadlet containers on `podman02` (built from the repo-root `Dockerfile`, one image, two containers — the Intune container overrides the image's default `CMD` via the quadlet's `Exec=`), fronted by Caddy which terminates TLS and reverse-proxies to the container's plain-HTTP port. The servers themselves never see TLS directly. Client-facing URLs are `https://jamf-mcp.colgate.edu/mcp` and `https://intune-mcp.colgate.edu/mcp` — internal DNS only, no public exposure, and several JAMF tools are destructive, so `/mcp` also requires a bearer token (see Environment Variables) on top of the network restriction — defense in depth, not a substitute for it. Deploy/redeploy playbooks live in `IAC/ansible-servers/linux/apps/desktop-management-mcp.yml` (full deploy) and `desktop-management-mcp-update.yml` (code-only redeploy); see `IAC/CLAUDE.md` for the broader Terraform → Ansible dispatch pipeline.

Both quadlets are rendered from **one shared env file** (`/etc/desktop-management-mcp/desktop-management-mcp.env`, one Ansible template, one set of vars) — so despite `ENTRA_OAUTH_ENABLED` reading as a per-server toggle in code, there is currently no way to enable Entra auth for jamf-mcp without also enabling it for intune-mcp, or vice versa. This is a known gap versus the original rollout plan (which assumed independent enablement), left as-is because it's low-risk while role assignment is still solo-testing scale — no one has an `Intune.*` role yet. Splitting into two env files (or two env-var names) would be needed to truly decouple this before a wider pilot.
